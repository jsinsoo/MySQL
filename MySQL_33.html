성취기준

3. 수업 시작 이야기

📚 인문학자의 이야기 — 고쳐 쓴 기록이 더 오래 남는다

위대한 글과 기록도 처음부터 완벽하지 않았습니다. 초고를 읽고, 틀린 표현을 찾고, 더 정확한 문장으로 고쳐 쓰는 과정이 있었기에 오래 남는 작품이 되었습니다.

테스트는 프로그램의 부족함을 들춰내는 일이 아니라 더 오래 사용할 수 있게 다듬는 과정입니다.

🏛 철학자의 이야기 — 의심은 부정이 아니라 더 깊은 이해의 시작이다

철학자는 당연해 보이는 주장에도 질문을 던집니다. “정말 모든 경우에 그런가?”, “예외는 없는가?”라는 질문이 사고를 깊게 만듭니다.

테스트도 같은 태도입니다. 잘 작동하는 한 번의 결과보다 실패할 수 있는 여러 조건을 생각하는 힘이 중요합니다.

🔬 과학자의 이야기 — 반복 가능한 실험이 신뢰를 만든다

과학적 결과는 우연히 한 번 성공한 것으로 충분하지 않습니다. 같은 조건에서 반복하고, 경계 조건과 오차를 확인하며, 실패한 실험도 기록해야 합니다.

프로그램 테스트 역시 정상·경계·예외 상황을 반복해 검증할 때 신뢰할 수 있습니다.

➗ 수학자의 이야기 — 반례 하나가 명제를 다시 생각하게 한다

수학에서 수많은 사례가 맞아도 단 하나의 반례가 있으면 명제는 다시 검토해야 합니다. 프로그램도 대부분의 입력에서 잘 작동하더라도 한 경계값에서 오류가 나면 개선이 필요합니다.

테스트는 프로그램의 반례를 찾고 더 정확한 조건을 세우는 논리적 탐구입니다.

교사의 시작 이야기

오늘은 여러분의 프로그램을 비판하는 시간이 아니라 지켜 주는 시간입니다. 오류를 찾는 것은 실패를 확인하는 일이 아니라 사용자가 만나기 전에 우리가 먼저 발견하는 책임 있는 행동입니다. 좋은 개발자는 오류가 없는 사람이라기보다 오류를 재현하고 기록하며 고칠 수 있는 사람입니다.

def has_overlap(
    equipment_id,
    start_time,
    end_time
):
    conn = get_connection()
    cur = conn.cursor()

    cur.execute('''
    SELECT COUNT(*)
    FROM reservations
    WHERE equipment_id = %s
      AND approval_status IN (
          'pending',
          'approved'
      )
      AND start_time < %s
      AND end_time > %s
    ''', (
        equipment_id,
        end_time,
        start_time
    ))

    count = cur.fetchone()[0]

    cur.close()
    conn.close()

    return count > 0

트랜잭션 롤백 테스트

일부 변경 후 오류가 발생했을 때 rollback()으로 이전 상태로 돌아가는지 확인합니다.

def test_transaction_rollback():
    conn = get_connection()
    cur = conn.cursor()

    try:
        conn.start_transaction()

        cur.execute(
            '''
            UPDATE equipment
            SET status = 'repair'
            WHERE equipment_id = %s
            ''',
            (1,)
        )

        raise RuntimeError("의도한 테스트 오류")

    except RuntimeError:
        conn.rollback()
        print("롤백 테스트 통과")

    finally:
        cur.close()
        conn.close()

존재하지 않는 데이터 처리

조회 결과가 없을 때 None을 그대로 사용하지 않고, 성공 여부와 안내 메시지를 포함한 구조로 반환합니다.

def find_equipment(equipment_id):
    conn = get_connection()
    cur = conn.cursor(dictionary=True)

    cur.execute(
        '''
        SELECT equipment_id,
               equipment_name,
               status
        FROM equipment
        WHERE equipment_id = %s
        ''',
        (equipment_id,)
    )

    equipment = cur.fetchone()

    cur.close()
    conn.close()

    if equipment is None:
        return {
            "success": False,
            "message": "장비를 찾을 수 없습니다."
        }

    return {
        "success": True,
        "data": equipment
    }

준비된 문장 보안 점검

문자열을 SQL 문에 직접 이어 붙이지 않고 매개변수로 전달하여 SQL 삽입 공격 위험을 줄입니다.

def search_equipment(keyword):
    conn = get_connection()
    cur = conn.cursor(dictionary=True)

    sql = '''
    SELECT equipment_id,
           equipment_name,
           category
    FROM equipment
    WHERE equipment_name LIKE %s
    '''

    cur.execute(
        sql,
        ("%" + keyword + "%",)
    )

    rows = cur.fetchall()

    cur.close()
    conn.close()

    return rows

6. 수업 끝 이야기

🌙 시인의 이야기 — 지운 단어도 시를 완성한다

시는 더한 문장만으로 완성되지 않습니다. 어울리지 않는 단어를 덜어 내고 리듬을 고치는 과정도 작품의 일부입니다. 프로그램에서도 불필요한 기능을 삭제하는 것이 때로는 최고의 개선입니다. 단, 제출 버튼까지 삭제하면 선생님이 매우 서정적으로 당황합니다.

📖 소설가의 이야기 — 복선이 회수되지 않으면 독자는 기억한다

소설의 작은 설정도 끝까지 연결되어야 이야기가 설득력을 얻습니다. 프로그램의 버튼, 데이터, 메시지도 서로 맞지 않으면 사용자는 즉시 알아차립니다. 테스트는 흩어진 복선을 하나의 완성된 이야기로 연결합니다.

🎭 희곡인의 이야기 — 실수한 배우를 탓하기보다 동선을 고친다

좋은 연출가는 실수가 반복될 때 배우만 탓하지 않고 무대 구조와 동선을 함께 살펴봅니다. 오류도 사용자 탓으로 돌리기보다 입력 안내와 화면 구조를 개선해야 합니다.

🎬 연극인의 이야기 — 리허설의 박수는 문제를 찾았을 때 나온다

리허설에서는 실수를 발견하는 것이 성공입니다. 본 공연 전에 조명과 음향의 문제를 찾았기 때문입니다. 테스트 실패 문구는 야유가 아니라 “지금 발견해서 다행이다!”라는 박수입니다.

🎼 음악인의 이야기 — 조율은 연주를 늦추지 않고 아름답게 만든다

악기를 조율하는 시간은 공연을 방해하는 시간이 아닙니다. 서로 다른 음을 맞추어 더 좋은 합주를 만드는 시간입니다. 테스트와 개선도 프로그램의 조율입니다. 다만 오류가 100개라면 오늘의 장르는 실험 음악일 수 있습니다.

성장은 틀리지 않는 데서 오지 않습니다. 틀린 이유를 외면하지 않고 다시 시도하는 데서 옵니다. 테스트 결과의 빨간 표시도 여러분의 능력을 평가하는 낙인이 아니라 다음 행동을 알려 주는 신호입니다.
